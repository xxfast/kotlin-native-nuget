# A top-level function named `signal` silently fails to resolve at runtime on mingwX64

**Verified by execution** (mingwX64, 2026-09-05): a top-level `fun signal(dbm: Int)` is exported as `@CName("signal")`, `nm` shows `T signal` defined in the built `test.dll`, but the DLL's export-name table (`objdump -p`) does not list `signal` alongside every sibling export, so the generated C# `[DllImport(EntryPoint = "signal")]` throws `EntryPointNotFoundException` at runtime with no build-time diagnostic at all: KSP succeeds, the Kotlin `@CName` export succeeds, and the C# compiles. The inferred cause is a name collision with the C runtime's own `signal()` (`<signal.h>`), though the CRT-thunk-vs-plugin-symbol mechanism was not fully confirmed; only mingwX64 was built, macOS is unverified either way. `nuget-processor` has no reserved-symbol list for libc/CRT names, only the C-*keyword* suffixing in `Reserved.kt:25` (a different list, see the top-level-camelCase item), so nothing catches a Kotlin identifier that happens to collide with a platform runtime export. It went unnoticed because no existing fixture used a name that collides with a well-known libc symbol; the ADR-074 amendment's collar-signal fixture sidestepped it by renaming to `collarSignal` rather than fixing it. Discovered alongside [ADR-074](https://github.com/xxfast/kotlin-native-nuget/blob/main/docs/adr/074-expect-actual-declarations.md)'s 2026-09-05 amendment.
