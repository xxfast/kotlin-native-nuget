# `Tier1InterfaceBridgeFactoryTest`'s nested-enum gate looks stale against ADR-133/134

> Discovered by the documenter while closing out the ADR-066 stale-nesting-strings wording fix (2026-09-19). Inferred by reading source; not confirmed by running the test, since the worktree's Gradle lock belonged to a concurrent refactorer run.

`Tier1InterfaceBridgeFactoryTest.kt`'s `enumSource` fixture nests `enum class Whistle` inside `interface Kettle`, and `an interface with an undeclared enum member gets no factory on either half` (~:262) asserts `kettle_bridge_create` and `KettleBridgeState` are absent, with the fixture's own KDoc (~:233-236) claiming "a nested enum is never declared in C#".

Reading `NugetProcessor.kt`'s nested-declaration walk directly: `NESTED_DECLARATION_KINDS` includes `ENUM_CLASS` (`:132-137`), and `unsupportedNestedOwnerReason()` (`:183-198`) no longer refuses an `interface` owner (ADR-134). Neither `Kettle` (the owner) nor `Whistle` (the candidate) hits any of `nestedDeclarationDeferral()`'s refusal arms, so by the same rule `docs/topics/enums.md` and `classes-and-objects.md` now document as current, `Whistle` should be walked into `nestedCandidates`, added to the `enums` bucket, and reach `exportedObjectHandles`, meaning `ForwardBridgeTypeClassifier.classify()` should return `BridgeType.Enum` for it, and `ForwardInterfaceBridgePlanner.bridgeType()` (`:179-198`, whose own comment "a nested enum ... is never declared as a C# enum at all" is the same stale claim) should plan the member rather than return `null`.

Neither the ADR-133 PR (`82b44380`) nor the ADR-134 PR (`112475a1`) touched `Tier1InterfaceBridgeFactoryTest.kt` or `ForwardInterfaceBridgePlanner.kt` (verified: neither file appears in `git show --stat` for either merge commit), unlike the `test-library/.../issue54/NestedListenerOwner.kt` and `NestedModeOwner.kt` fixtures, which both PRs left with an explicit "ADR-133 inverted the premise below" note plus updated `IntegrationTests/NestedEnumGateTests.cs`/`NestedInterfaceGateTests.cs` assertions. This fixture and `ForwardInterfaceBridgePlanner.kt`'s comment look like the same migration simply never reached them.

Left un-edited (both the test's KDoc and its assertions, and the planner's comment) because this needs a real test run to confirm whether the fixture is still green (some filter this reading missed keeps `Whistle` out of `exportedObjectHandles`) or actually red (the migration gap above), and because the assertions are test code, out of scope for a documentation-only lane.
