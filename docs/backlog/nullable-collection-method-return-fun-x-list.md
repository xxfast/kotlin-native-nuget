# A nullable collection method return (`fun x(): List<T>?`) has no planner route and is silently skipped, for every component type, not only value classes.

> Extracted verbatim from `ROADMAP.md` (Post-migration hardening) in the 2026-08-31 roadmap slim-down.

**A nullable collection method return (`fun x(): List<T>?`) has no planner route and is silently skipped, for every component type, not only value classes.** `ForwardCallablePlanner.nullableResultShape()` (`forward/ForwardCallablePlanner.kt:1308-1477`) has no `is BridgeType.Collection` branch and falls to its final `else -> null` (`:1477`), so the callable's result shape comes back `null` and the whole method is skipped rather than bound; the corresponding Kotlin emitter, `ForwardKotlinPlanEmitter.addNullableResult()` (`:574-693`), has no `Collection` branch either and would `error(...)` if the planner ever handed it one, confirming the gap is unreached dead code today, not a live crash. `Nullable(Collection)` already binds at a **property** (`ADR-075`) and as an ordinary **parameter** (constructor/method, same ADR), so this is narrower than it looks: only the **method-return** position is missing, and it is missing for every element/key/value type, `String` included, not something [ADR-081](docs/adr/081-value-class-collection-components.md) introduced or could have fixed within its own scope. No fixture in `test-library` declares a `List<T>?`/`Map<K,V>?`/`Set<T>?` method return, which is why this has gone unseen. Discovered alongside [ADR-081](docs/adr/081-value-class-collection-components.md), while reading `nullableResultShape()` to confirm the value-class collection-component read side didn't share this gap (it doesn't: `ChartBook.issuedCharts()` returns a non-nullable `List<ChartId>`).
