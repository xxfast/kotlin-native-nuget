# A missing constructor overload can silently resolve to the always-emitted `internal Foo(IntPtr handle)` wrapper constructor instead of failing to compile.

> Extracted verbatim from `ROADMAP.md` (Phase 5: Exception handling) in the 2026-08-31 roadmap slim-down.

**A missing constructor overload can silently resolve to the always-emitted `internal Foo(IntPtr handle)` wrapper constructor instead of failing to compile.** Verified by compile behaviour during [ADR-091](docs/adr/091-constructor-default-parameters.md)'s red step: `Interop.cs` compiles directly into the consumer assembly, and `internal` is assembly-visible rather than file-visible, so `internal Foo(IntPtr)` is a real overload candidate from inside `IntegrationTests`. A public one-argument call site with no matching public constructor can therefore bind to the handle constructor and fail as CS1503 (argument type mismatch) instead of CS7036 (no overload takes N arguments), a far less legible error for a consumer than "no such overload" would be. Benign today: no fixture declares a public constructor whose sole parameter is a single `IntPtr`, and none of ADR-091's synthesized omitting overloads happens to produce that one-`IntPtr`-parameter shape either, so nothing currently mis-binds. Same family as the two items above (an always-emitted member excluded from a collision/visibility check it should be checked against); left unfixed as out of ADR-091's scope, recorded here so the next feature that adds or removes a constructor overload near this family knows to check for it.
