# The propagated `KotlinException.KotlinStackTrace` carries dozens of host-process frames below the `@CName` entry point, unsymbolizable and actively misleading.

> Extracted verbatim from `ROADMAP.md` (Phase 5: Exception handling) in the 2026-08-31 roadmap slim-down.

**The propagated `KotlinException.KotlinStackTrace` carries dozens of host-process frames below the `@CName` entry point, unsymbolizable and actively misleading.** Observed in an external integration report (2026-08-20) on `mingwX64`: the Kotlin library's own frames symbolize fine (`kfun:org.example...Greeting#throwException...`, `greeting_throwException + 115`), but everything below the export is CLR/host memory the Kotlin runtime cannot name, printed either as `??? <address> 0x0 + <offset>` or, worse, attributed to the nearest known export (`_ZSt25__throw_bad_function_callv + 17963386`), which reads like a real C++ crash to a consumer. Not a propagation bug, ADR-027's trace crosses the bridge intact; it is Kotlin/Native capturing the full native stack while embedded in a foreign host. Candidate fix: trim the trace at the first `@CName` export frame before writing it into the `NugetError` envelope, since every frame below it belongs to the consumer's own process and the .NET half of the story is already on the C# exception. Needs a decision on whether to trim Kotlin-side (at capture) or C#-side (at `KotlinStackTrace` formatting), and a `mingwX64` fixture assertion that the trimmed trace still ends at the export frame.
