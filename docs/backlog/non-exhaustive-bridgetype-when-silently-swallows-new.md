# A non-exhaustive `BridgeType` `when` silently swallows a new sealed variant into whatever its `else` does; only an exhaustive `when` gets the compiler's help.

> Extracted verbatim from `ROADMAP.md` (Tooling & Test Integrity) in the 2026-08-31 roadmap slim-down.

**A non-exhaustive `BridgeType` `when` silently swallows a new sealed variant into whatever its `else` does; only an exhaustive `when` gets the compiler's help.** [ADR-076](docs/adr/076-instant-mapping.md)'s stated lesson, "add a *new* `BridgeType` variant rather than reuse one, so the compiler enumerates every `when`", only pays off at a `when (type)` with no `else` branch: Kotlin then refuses to compile until every sealed case is handled. A `when` that already ends in a catch-all `else` compiles either way, and a newly added variant falls into whatever the `else` does without a compiler nudge. Implementing [ADR-088](docs/adr/088-kotlin-implemented-interfaces-at-forward-positions.md)'s `BridgeType.BoundInterface` hit exactly this at three sites that had to be found and patched by inspection rather than by a build failure: `ForwardCallablePlanner.skipReason()`'s nested `is BridgeType.Nullable` arm (`ForwardCallablePlanner.kt:1801`, would have reported the generic `NULLABLE` skip reason, whose hint talks about `Boolean`, instead of naming the position); `ForwardCallablePlanner.inputSkipReason()`'s mirror on the parameter side (`ForwardCallablePlanner.kt:1897`); and `ForwardMarshallingModel.requiredConversion()`'s terminal `else -> null` (`ForwardMarshallingModel.kt:508`, would have told the validator "no conversion required" for a type whose transfer is tagged `GC_HANDLE_TO_BOUND_VALUE`, a build-time crash rather than silent wrong output, but still a site the compiler could not catch). Not (yet) audited: whether other non-exhaustive `BridgeType` `when`s outside these three carry the same latent hazard for the *next* new variant. See [ADR-088](docs/adr/088-kotlin-implemented-interfaces-at-forward-positions.md)'s Implementation Addendum for the full list found this round. Distinct from the item above (which is about `BridgeType` *adoption* by the legacy protocols): this one is about exhaustive-`when` *coverage* within the code that already consumes `BridgeType`
