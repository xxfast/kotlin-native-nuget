- [x] **There is no export set: the processor bridges every public declaration it can see.** `NugetProcessor.process()` takes `resolver.getAllFiles()` with no filter, which is the line above meant literally — *all* public declarations. The `rootPackage` in `nuget { publish { } }` looks like the scoping knob and is not one: it only ever feeds `mapPackageToNamespace` (Phase 3), so it renames the C# namespace while the declaration set stays global, and that function even has an explicit branch that maps a package *outside* `rootPackage` anyway. Applying the plugin to a module that also holds unrelated public API therefore tries to bridge that API too, and any construct the forward direction cannot express there becomes a build break in generated code the user never wrote. This is MF-001 (declaration-level export scoping): an include/exclude mechanism, an annotation, or an effective package filter. First consumer to hit it was NYTimes-KMP (its BUG-003), which pays for it with a dedicated `:app:windows` export module whose `build.gradle.kts` carries a `TODO` explaining why the module exists at all. Verified directly: `getAllFiles()` and every `rootPackage` use site were read in source. Prior art for the decision is Swift Export and ObjC Export, which both had to answer "which declarations leave the module". **Done:** [ADR-063](docs/adr/063-forward-declaration-level-export-scoping.md) adds `publish { include(...); exclude(...) }`, mirroring `bind { include/exclude }` verb-for-verb (exclude wins, prefix match); an empty `include` defaults to `rootPackage` when set, so `rootPackage` now scopes as well as renames (a deliberate, documented behaviour change). A reverse-bound package (from `dependencies { dependency(...) { bind { } } }`) is always exported regardless of `include`/`exclude`, since `test-library`'s own forward/reverse round trip broke on the first cut of this feature when a bound package was dropped from scope.

Neither Phase 9 nor Phase 10 listed this; discovered while validating the Phase 13 interface item, which is **blocked** on it. Explicitly **not** in scope: Kotlin *implementing* the interface and passing it back to C# — that stays Phase 7 line "Support implementing **C#-declared** interfaces in Kotlin" / Phase 13 "Implement a C#-defined interface in Kotlin and pass it back to C#", both of which stay open. **Done:** [ADR-070](docs/adr/070-csharp-interfaces-in-kotlin.md) generates a pure Kotlin `interface` per admissible bound `RirInterface`, plus a handle-backed `IFooHandle` implementation (the Xamarin Java-binding "Invoker" shape) dispatching each member through a per-interface registration slot table, structurally identical to a class's. ## Tooling & Test Integrity

Fallout from [ADR-053](docs/adr/053-nullable-reference-types-in-kotlin.md) (reverse nullability), the first fixture to exercise the reverse bridge realistically. It flushed out four latent defects, **two of which were phantoms of stale build state**, and the debugging cost was dominated by having no way to observe the bridge and no way to trust the build. These items exist so the next feature does not pay that cost again.

**Rejected: a `scripts/verify.sh --fast` mode.** It was proposed on the theory that agents hand-patch generated output and the NuGet cache because the sanctioned path is too slow. Measurement kills that theory: verify is 38s clean-room after a source change, 18s warm. Nobody cheats to save 14 seconds. Agents did it because they were being sloppy, which is a discipline problem, and the `PreToolUse` guardrail now makes it impossible. Worse, the only real saving came from skipping `:test-library:clean`, which is precisely what produces a truncated `Interop.cs` (see the KSP bug below), so a fast mode would have handed agents a *sanctioned* way to manufacture the phantom bugs this whole section exists to prevent. Do not re-add it.

- [x] **Reverse-bridge registration observability: always-on self-check first, trace second.** The [ADR-041](docs/adr/041-kotlin-to-csharp-call-mechanism.md) function-pointer table was unobservable: nothing could report which `nuget_{ns}_{type}_register` exports actually fired, so "did registration work?" was only answerable by bisecting. The research found that an opt-in trace, the original framing of this item, is the weaker half of the fix: nobody enables a trace for a bug they don't already suspect, and in the ADR-053 hunt nobody suspected registration. What would actually have caught it is **always-on**, no env var required: every register export now carries a registration-time contract self-check (`slotCount: Int` and `contractHash: Long`, amending [ADR-048](docs/adr/048-kotlin-stub-generation-from-reverse-ir.md)'s and [ADR-049](docs/adr/049-csharp-registration-shim-generation.md)'s registration contract), which refuses to store any pointer and fails loud, naming both sides, the instant a stale C# shim and a freshly built native library disagree; and a generated `NugetRegistry` that turns the old constant "bindings are not registered" message into a computed "N of M registrations fired", naming exactly which types are missing so a whole-assembly problem (nothing fired) is never confused with a single-type problem (everything but one fired). Tier 1 diagnostic-mode assertions cover both permanent cells (23 now green; 21 stays `@XFail`, see line 97 below) plus each newly-named skip (`Tier1DiagnosticCellsTest`, `Tier1NamedSkipDiagnosticsTest`)

- [x] **KSP incremental processing silently drops suspend functions from `Interop.cs`.** `NugetProcessor.kt` partitioned functions into `suspendFunctions` / `regularFunctions`, but omitted `suspendFunctions` from **both** `hasNothingToProcess` and the hand-maintained `sources: Array<KSFile>` feeding `Dependencies(aggregating = true, *sources)`. Three defects traced to that one omission, not one: (1) `hasNothingToProcess` checked 13 declaration buckets and skipped `suspendFunctions`, so a module whose *only* public API is top-level `suspend fun`s (no class, object, etc.) generated nothing at all on a clean build, with no diagnostic, confirming the suspected second manifestation this item originally guessed at; (2) the same 13-of-14 `sources` list meant KSFiles holding only suspend functions were never declared as dependencies of the aggregating output, so KSP dropped them on an incremental run, reproduced by touching any `test-library` source and running `:test-library:packNuget` without `clean`, which came back missing the `AsyncFunctions` and `AsyncExceptions` classes (the only two forward fixture files containing solely top-level `suspend fun`s; every other suspend-carrying file also declares a class and survived via the `classes` bucket) with consumers then failing `CS0103`; (3) newly found while fixing the above, the sibling `CNameExports.kt` write passed `Dependencies(aggregating = true)` with **no** originating files at all, so it contributed zero files to KSP's dirty set and survived only because `Interop.cs`'s declared list happened to dirty the same files in the same round, meaning the Kotlin `@CName` half lost the suspend exports in lockstep with the C# half, which is exactly why ADR-055's forward ABI contract check stayed green throughout and the failure only ever surfaced as a consumer-side `CS0103`. - [ ] **KotlinPoet's `addCode(String)` parses `%` as a format placeholder even on the no-varargs overload.** Any generated Kotlin containing a literal `%` (e.g. a modulo operator) must escape it as `%%` or codegen breaks. **Verified**: hit and fixed in `exports/GenericClassExports.kt` while emitting `instantFromDotNetTicks`, whose `sinceEpoch % 10_000_000L` needed escaping ([ADR-076](docs/adr/076-instant-mapping.md)). - [ ] **Nothing checks that two packaged targets generate the same C# API, and after [ADR-074](docs/adr/074-expect-actual-declarations.md) they can legitimately differ.** `packNuget` packages exactly one target's `Interop.cs` ("Pick the first available target's output", `NugetPlugin.kt:331-339`; **Verified**, read in source) while shipping *every* target's binary, so the single packaged C# API is the contract every platform's `.dylib`/`.dll` must satisfy. That was harmless while the export set was target-independent. ADR-074 makes the `actual` the forward export root, and an `actual` may legally declare public members its `expect` never mentioned, so two targets can now produce genuinely different C# APIs and only one of them ships. A member present in the packaged target's `actual` but absent from another's generates a `[DllImport]` that resolves to a missing entry point on that platform: a runtime `EntryPointNotFoundException`, not a build error. Neither existing guard can catch it, and for structural reasons rather than by omission: `ForwardAbiContract` ([ADR-055](docs/adr/055-forward-abi-contract-check.md)) compares the C# and Kotlin halves generated in the **same** run, and each target's run is internally consistent; a single KSP run cannot see it either, because the other target's source set is not in the compilation (**Verified** by spike, `getAllFiles()` for `kspKotlinMacosArm64` lists only `commonMain`, `nativeMain` and `macosArm64Main`). Fix is a plugin-level check, not a processor one: run KSP for every packaged target and diff the ADR-055 forward ABI contract manifests, failing generation when they disagree. Note this is not exclusively an `expect`/`actual` concern; ADR-074 is what makes it reachable through ordinary, correct Kotlin rather than only through a hand-written per-target source set. ADR-074's Decision 3 (a top-level `actual` takes its C# static class name from the `expect`'s file) removes the most likely *accidental* instance, the per-target file name, but not the general case. Split out of [ADR-074](docs/adr/074-expect-actual-declarations.md) with the human, deliberately out of that feature's scope.

## Future Improvements

- Support flat/unnested sealed class hierarchies (subclasses as top-level in same namespace)
- KSP incremental processing if build times become a concern on large libraries. Has a prerequisite now: the forward processor's two generated outputs declare `Dependencies.ALL_FILES` (see the completed item above, `NugetProcessor.kt`), which deliberately opts the processor out of incrementality to close a dropped-suspend-functions bug permanently. Any future incrementality work must first restore a correct, complete per-file dependency set instead of a hand-maintained bucket list, the exact mistake that caused the bug
- Map data classes to C# `record class` if a safe `with`-expression pattern can be found (see [ADR-008](docs/adr/008-data-class-mapping.md))
- Verify Kotlin GC actually frees objects after all StableRefs are disposed (requires Kotlin-side weak references + GC trigger — not feasible in standard unit tests)
- Memory leak detection tooling for bridged objects in CI
- Object identity preservation (caching wrappers) if profiling shows allocation overhead is significant
- Custom type mappers for arbitrary third-party dependency types the plugin will never hardcode (escape hatch). Known stdlib types such as `kotlin.time.Instant` are Phase 4 first-class mappings instead, not this item
- Pure-JVM ECMA-335 metadata reader + NuGet v3 client, dropping the .NET SDK prerequisite from the Kotlin-side build (synthesis D1) — no plugin in this space runs prerequisite-free; a genuine ergonomic edge
- Hand-written C# shim escape hatch for API members outside the auto-bridgeable subset (spm4Kmp's bridge-folder model, synthesis D2)
- Forward un-skip/remap escape hatch: a Xamarin-`Metadata.xml`-style (or `@HiddenFromObjC`-style opt-out) mechanism to force-bind or remap a construct [ADR-064](docs/adr/064-forward-unsupported-declaration-diagnostics.md) would otherwise skip. Deferred by ADR-064's Scope; today the diagnostic's hint text names the hand-written-adapter workaround instead, the same choice ADR-043 made for reverse
- Reverse-bridge integration tests against real published NuGet packages (not just the controlled `TestDependency` fixture) — chosen precisely because they *don't* fit the bridgeable subset cleanly, to prove the ADR-043 skip diagnostics and partial-binding behaviour on messy real-world surfaces (mixed bridgeable/unbridgeable members, legacy nullability, multi-TFM)
- Map KDoc annotations to C# XML docs for better IDE support
- Expose Kotlin `Job` as a mapped C# type so cancellation can be tied to the job directly (e.g., `job.Cancel()`) instead of requiring a pre-created `CancellationTokenSource`
- NativeAOT compatibility for the generated bindings (see [ADR-038](docs/adr/038-aot-compilation.md)) — blocked on a reflection-free generics dispatch path; `[DllImport]` → `[LibraryImport]`; AOT publish smoke test in CI
- Centralize version-sensitive C# tokens into a `CSharpProfile` so the output dialect (interop attribute, native-int type, generic dispatch strategy) is a generation-time choice rather than hardcoded across the renderers — the enabler for AOT and any future C# dialect (see [ADR-038](docs/adr/038-aot-compilation.md))
