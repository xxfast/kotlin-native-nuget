# Two exported types with the same simple name in different packages collide on their export symbol: a constructor, a top-level function, and a sealed class all hit this.

> Extracted verbatim from `ROADMAP.md` (Phase 4: Rich type support) in the 2026-08-31 roadmap slim-down.

**Two exported types with the same simple name in different packages collide on their export symbol, and both a constructor and a top-level function hit this.** `ForwardCallablePlanner.constructorEntries` derives the export prefix from `cls.simpleName.asString().lowercase()` with no package qualifier, so two exported classes named `Kitten` in different packages both export `kitten_create` and fail `packNuget` with `Forward ABI duplicate C# import for kitten_create`. Same family, pre-existing: a bare top-level function export is `toCName(name)` with no package or file qualifier either, so two same-named top-level functions in *different* packages hit the same duplicate-export guard (a same-package pair is the numbering the item above now handles; a cross-package pair is untouched by it). **Verified by a real build failure**: hit by [ADR-095](docs/adr/095-static-route-overloads.md)'s own fixture, where a second `Kitten` (the extension-overload receiver) collided with the pre-existing `cat.Kitten`; worked around by renaming the fixture receiver to `Mitten`/`Tomcat` rather than fixing the underlying prefix scheme. Recorded in the ADR's Consequences, not spiked. Fix shape is presumably qualifying the export prefix by package, mirroring the numbering scope the item above already gives top-level/extension symbols.

**A third shape hits the same hazard: two sealed classes with the same simple name in different packages crash KSP.** `SealedClassExports.kt:27` derives the sealed-class export prefix the identical way (`sealed.simpleName.asString().lowercase()`, no package qualifier), so a second `LoadState` sealed class in a different package from an existing one collides on `loadstate_get_type` and every other `loadstate_*` export. Unlike the class/top-level cases above, which fail with `packNuget`'s duplicate-C#-import message, this one fails earlier and differently: `ForwardAbiContract.assertMatches` (`ForwardAbiContract.kt:80`) asserts `expected.size <= 1` per export name and throws `Forward ABI duplicate C# import for loadstate_get_type: [...]`, the same guard, so the build still fails rather than silently corrupting output, but at the sealed-class prefix computation specifically. **Verified**: hit while building the [#56](https://github.com/xxfast/kotlin-native-nuget/issues/56) part 2 fixture (a second `LoadState`, later renamed to `Issue56LoadState` to work around it rather than fix the prefix scheme, mirroring the `Kitten`/`Mitten` workaround above). Discovered alongside [ADR-107](docs/adr/107-throwable-property-mapping.md). Same fix shape as the rest of this item: qualify the sealed-class export prefix by package.
