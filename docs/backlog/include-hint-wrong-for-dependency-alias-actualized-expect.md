# The `include(...)` hint is wrong for a hypothetical dependency alias-actualized expect

**If a dependency klib's metadata carries an `expect` declaration and a consumer reference resolves to it, the reference misses the module-local `actualTypeAliasTargets` map** (`NugetProcessor.kt`'s `actualTypeAliasTargets`, built ~lines 338-355 alongside `expectsByName`, since that map is only ever populated from the current module's own `KSTypeAlias`/`isActual` declarations), falls through the `ForwardReachabilityClosure.kt` guard (`if (classDeclaration.isExpect) return`, ~line 162, which stops the walk before the declaration would otherwise be admitted), and surfaces as `SKIPPED_UNEXPORTED_DEPENDENCY_TYPE` with its standard `include(...)` hint. That hint tells the consumer to add the type's package to `include(...)`, which cannot fix this case: the type is an `expect` whose actualization lives in a dependency the consumer does not control, not a same-module type merely outside the configured export scope. This is a message defect (wrong remediation text), not wrong generated output; the declaration is correctly left unbridged either way. Inferred, not spiked: [ADR-074](https://github.com/xxfast/kotlin-native-nuget/blob/main/docs/adr/074-expect-actual-declarations.md)'s own cross-module analysis could not settle whether a dependency klib's metadata even retains the `expect` half (Tier 1's single-target JVM harness proves nothing about klib metadata), so this item's premise itself is unverified; it is recorded because the guard and the wrong hint text both exist in source regardless of whether the triggering condition is ever reachable. Discovered alongside ADR-074's 2026-09-05 amendment.
