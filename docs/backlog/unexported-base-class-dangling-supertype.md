# The identical hole exists for an unexported base class: `class X : UnexportedBase()` renders a dangling supertype

> Extracted verbatim from `ROADMAP.md` (Phase 2).

**The identical hole exists for an unexported base class: `class X : UnexportedBase()` renders `public class X : UnexportedBase` and fails the same CS0246, and the interface-only fix above does not close it.** Root cause: `forwardSuperClass()` (`ForwardClassMembership.kt:24-30`) returns the first non-`Any` `ClassKind.CLASS` supertype with no export-set check, and it is the *shared* has-superclass predicate four sites read in agreement: `CirClassTranslator.kt:55`, `ForwardCallablePlanner.kt:706` (also `:746`, where `isOverride` derives from it), `ForwardPropertyPlanner.kt:91`, and `ClassExports.kt:52`. Gating only the translator's `superClassDeclaration` would desync the four: the renderer would treat the class as base-less while the planner still emits `override` against no base (`CS0115`) and still declines to plan the inherited members the class would now have to carry itself. The fix has to thread the export set through `forwardSuperClass()` itself and all four call sites, not patch the translator alone; whether the planners' existing `ForwardBridgeTypeContext.exportedObjectHandles` (`NugetProcessor.kt:487-489`) is the same set as the translator's `exportedTypes` is not verified and must be checked before reusing it. Went unnoticed because no shipped forward fixture exercises a base class declared outside the export set; the interface-only shape above is the first thing to name this class of bug at all. Verified by source reading only, not runtime-reproduced. Discovered alongside [ADR-101](docs/adr/101-unexported-supertype-skip.md).
