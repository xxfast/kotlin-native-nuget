# Whether Kotlin frees an ADR-088 bound-interface transfer `GCHandle` when the callee throws is unverified either way.

> Extracted verbatim from `ROADMAP.md` (Phase 13: Reverse bidirectional — implementing C# contracts in Kotlin) in the 2026-08-31 roadmap slim-down.

**Whether Kotlin frees an ADR-088 bound-interface transfer `GCHandle` when the callee throws is unverified either way.** `boundInterfacePrelude` (`forward/ForwardCirPlanProjection.kt:695`) deliberately allocates the transfer `GCHandle` with no matching C#-side cleanup, by design: the comment there states the *receiving* side owns it, Kotlin's `nuget{Iface}Value` either frees it itself (token-probe hit) or hands it to the ADR-070 wrapper's cleaner, so adding a C#-side dispose to the `try`/`finally` scope this feature built would double-free. That ownership hand-off was not itself re-examined here: whether the Kotlin-side native call still transfers (or frees) the handle correctly when it throws *before* reaching the point that would normally take ownership is a Kotlin-side question this feature's C#-side fix did not touch and did not verify. Found while auditing every `ForwardCirHandleStep` prelude for the exception-safety fix above, which is why `boundInterfacePrelude` deliberately contributes no `cleanup` to `forwardCirHandleScope`. Discovered alongside no ADR, a documentation-only note on [ADR-088](docs/adr/088-kotlin-implemented-interfaces-at-forward-positions.md)'s bound-interface transfer handle.

**C#-side finding (2026-10-12, inferred, verified by reading only, not reproduced).** The same prelude also strands the transfer handle on the C# side when the call throws before Kotlin receives it. `boundInterfacePrelude` (`forward/ForwardCirPlanProjection.kt:1365-1366`) and the property route (`forward/ForwardCirPropertyProjection.kt:770`) emit `IntPtr xHandle = GCHandle.ToIntPtr(GCHandle.Alloc(x));` as a flat prelude line with no cleanup. If the call then throws before the native call returns (a closed wrapper refused by the `SafeHandle` marshaller, or a later argument's inline `?? throw`), nothing frees the handle and the C# implementation object stays rooted. In the regenerated `Interop.cs`, `Farm.Adopt(IFeedable)` allocates `feedableHandle` and then passes `_handle` with no disposed check. A plain catch-and-free would double-free on the path where Kotlin has taken the handle and then reports an error, so it needs its own decision, which depends on the Kotlin-side question above. Found while fixing the suspend completion handle leak ([ADR-210](../adr/210-flow-and-suspend-lambda-parameters.md)'s 2026-10-12 amendment), which does not touch this prelude.
