# A returned collection's result handle leaks if materialization throws mid-loop.

> Extracted verbatim from `ROADMAP.md` (Phase 4: Rich type support) in the 2026-08-31 roadmap slim-down.

**A returned collection's result handle leaks if materialization throws mid-loop.** `collectionMaterializingCore` (`forward/ForwardCirPlanProjection.kt:1134`) builds `List`/`Map`/`Set` results by walking `listHandle`/`mapHandle`/`setHandle` in a `for` loop and only calls `NugetListNative.Dispose`/`NugetMapNative.Dispose`/`NugetSetNative.Dispose` as the loop's last statement, after every element has been read; a component read that throws partway through (a value-class element whose reflective reconstruction fails, or any other component conversion) leaves the result handle's own `Dispose` unreached. The read-side mirror of the parameter-side leak this feature just fixed, on the *result* handle instead of the argument handles: the fresh `ForwardCirHandleScope.forwardCirHandleScope` wrapping covers only the `prelude`/`cleanup` built for parameters, not the materialization loop's own handle. Verified by source reading only, not runtime-reproduced. Discovered while building the collection-parameter exception-safety fix above, reading `collectionMaterializingCore` to confirm it shared no code path with the parameter side. **Now runtime-observable rather than only inferred:** [ADR-099](docs/adr/099-nested-collection-components.md)'s red run reproduced it with a stack trace (`NugetListNative.Dispose(listHandle)` sitting after the materialize loop with no `try`/`finally`), and its new `finally`-guarded `ReadList`/`ReadSet`/`ReadMap` helpers mean the leak is **not reproduced per nesting level** for a nested collection, since every inner level now goes through one of those helpers. The **outer** level is unchanged and still leaks; routing the outer materialization loop through the same helpers, which ADR-099 deliberately left out of scope, would close it as a two-line change.
