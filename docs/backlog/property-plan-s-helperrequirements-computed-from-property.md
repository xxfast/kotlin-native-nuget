# A property plan's `helperRequirements` is computed from the property's declared type only, ignoring its receiver's type, and nothing currently checks it.

> Extracted verbatim from `ROADMAP.md` (Post-migration hardening) in the 2026-08-31 roadmap slim-down.

**A property plan's `helperRequirements` is computed from the property's declared type only, ignoring its receiver's type, and nothing currently checks it.** `ForwardPropertyPlanner.propertyPlan`'s `helperRequirements = when (type.unwrapNullable()) { ... }` (`forward/ForwardPropertyPlanner.kt:251-264`) switches on the property's own type, never the receiver (relevant for an extension property, where the receiver can independently need its own helper, e.g. `VALUE_CLASS`/`ENUM_ORDINAL` for a value-class receiver). Inert today for two independent reasons: only `ForwardHelperRequirement.COLLECTION` and `INSTANT` are ever read back out of a property plan's `helperRequirements` (`NugetProcessor.kt:1007-1071`), and `ForwardPropertyPlan.validate()` never checks `helperRequirements` at all (unlike `ForwardCallablePlan`'s own `validate()`, which asserts `requiredConversion.helper() in plan.helperRequirements` for every transfer, `forward/ForwardMarshallingModel.kt:397`). So a value-class-receiver property plan with a helper-less `helperRequirements` set does not currently fail validation or omit a needed generated helper class. Becomes a trap only if property-plan validation ever grows the same callable-side check: at that point a receiver-driven helper need (e.g. an enum-underlying extension-property receiver's ordinal helper) would need to be threaded in, or plans would start failing `validate()` for value-class receivers that work correctly today. Verified in source. Discovered during value-class-receiver research (no ADR, mirror of [ADR-077](docs/adr/077-value-classes-at-ordinary-positions.md)).
