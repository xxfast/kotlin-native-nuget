# `fun dispose()` collides with the generated `Dispose` as a named entry-point collision, not `ERROR_CSHARP_SIGNATURE_COLLISION`.

> Extracted verbatim from `ROADMAP.md` (Phase 5: Exception handling) in the 2026-08-31 roadmap slim-down. Amended 2026-09-08 after [ADR-117](../adr/117-forward-abi-collision-names-owning-declarations.md) fixed the headline defect.

**Fixed by ADR-117:** `class Closer { fun dispose() {} }` used to abort `NugetProcessor.process()` with a raw `java.lang.IllegalArgumentException: Forward ABI duplicate C# import for closer_dispose` (`ForwardAbiContract.kt:76`), naming only the mangled symbol. It now fails with a named `ERROR_C_ENTRY_POINT_COLLISION`, naming `sample.Closer.dispose()` and the generated `Dispose`, `sample.Closer (generated Dispose)`, as the two owners of `closer_dispose`, both with `file:line`, plus a rename hint (ADR-117's 2026-09-13 amendment replaced the earlier `sample.Closer (route-owned export: ...)` class-range text with this exact, role-labelled owner). `Tier1EntryPointCollisionTest`'s `fun dispose names the method and the generated Dispose` cell is the reproducer.

**Residual, not fixed:** the collision still fires as `ERROR_C_ENTRY_POINT_COLLISION`, the generic duplicate-entry-point kind, not `ERROR_CSHARP_SIGNATURE_COLLISION` (ADR-034's kind, used for two constructors or two methods that render an identical C# signature *within one class*). Whether a same-name-as-generated-`Dispose` collision deserves the more specific ADR-034 treatment, since it is really a "your name is reserved" case rather than an arbitrary cross-declaration symbol clash, was not decided; today's message is correct and actionable but generic. `fun close()` is unaffected and renders `public void Close()` alongside `public void Dispose()`, so the collision is specifically the `dispose`/`Dispose` name pair.

**A sealed arm's own `fun dispose()` hits the same hazard.** [ADR-116](../adr/116-sealed-subclass-methods-on-the-callable-plan.md) (sealed-subclass methods on the callable plan) put a sealed arm's own declared methods on the same `ForwardCallablePlanner` route an ordinary class method uses, and the sealed subclass block already always declares `public override void Dispose()`. Verified no guard exists anywhere against a member literally named `dispose` (`grep '"dispose"'` over the planner, translator and renderer is empty for the sealed route, same as the ordinary-class route above), so `data class Running(...) : Job() { fun dispose() {} }` is Inferred to hit the same `job_running_dispose` entry-point collision the ordinary-class case does, now reported as `ERROR_C_ENTRY_POINT_COLLISION` with the arm named as `sample.Job.Running (generated Dispose)` (ADR-117's 2026-09-13 amendment gives the sealed route the same exact-owner-plus-role naming the ordinary-class route gets, not only the class-level range the original ADR shipped), not reproduced by a fixture. Not fixed by ADR-116 or ADR-117; recorded here rather than as a second backlog item since it is the same underlying hazard, just reached from the sealed route too.

**Correction, both here and in the constructor/top-level/sealed-class backlog:** the original "no invalid `Interop.cs` is written" fail-safe claim was imprecise. `Interop.cs` **is** written before the ABI contract check runs (`NugetProcessor.kt`'s `generateCSharpBindings` writes it, then `assertMatches`/`csharpLegacy` run after). What is actually guaranteed is narrower: the KSP round fails and `CNameExports.kt`, the Kotlin `@CName` export file, is never written, so `packNuget` (which needs that file) never runs and no inconsistent package ships.
