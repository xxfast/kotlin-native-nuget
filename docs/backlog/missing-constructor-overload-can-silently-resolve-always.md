# A missing constructor overload can silently resolve to the always-emitted `internal Foo(IntPtr handle)` wrapper constructor instead of failing to compile.

> Extracted verbatim from `ROADMAP.md` (Phase 5: Exception handling) in the 2026-08-31 roadmap slim-down.

**A missing constructor overload can silently resolve to the always-emitted `internal Foo(IntPtr handle)` wrapper constructor instead of failing to compile.** Verified by compile behaviour during [ADR-091](docs/adr/091-constructor-default-parameters.md)'s red step: `Interop.cs` compiles directly into the consumer assembly, and `internal` is assembly-visible rather than file-visible, so `internal Foo(IntPtr)` is a real overload candidate from inside `IntegrationTests`. A public one-argument call site with no matching public constructor can therefore bind to the handle constructor and fail as CS1503 (argument type mismatch) instead of CS7036 (no overload takes N arguments), a far less legible error for a consumer than "no such overload" would be. At the time this was written: no fixture declares a public constructor whose sole parameter is a single `IntPtr`, and none of ADR-091's synthesized omitting overloads happens to produce that one-`IntPtr`-parameter shape either, so nothing then mis-bound. Same family as the two items above (an always-emitted member excluded from a collision/visibility check it should be checked against); left unfixed as out of ADR-091's scope, recorded here so the next feature that adds or removes a constructor overload near this family knows to check for it.

**Verified, and no longer benign, for a sealed arm.** Every sealed arm [ADR-009](docs/adr/009-sealed-class-mapping.md) has ever generated carries *only* `internal Arm(IntPtr handle)`, never a public constructor at all, since a consumer is meant to reach an arm through the base's `FromHandle` discriminator or a factory method. In .NET 7+, `IntPtr` is `nint`, and an `int` converts to `nint` implicitly, so a call like `new Purr.On(9)` (`Purr.On` a nested sealed arm, from the [ADR-134](docs/adr/134-nested-types-under-deferred-owners.md) fixture) does not even hit the CS1503 mismatch the paragraph above describes: it compiles clean, binds to the internal handle constructor, and hands the bridge `9` as though it were a native stable-ref address, access-violating on the first call through it. This is not a confusing compile error, it is an apparently-successful build that crashes at runtime, and it applies to every sealed arm that has ever shipped, not a hypothetical one-`IntPtr`-parameter shape. Candidate fixes: an `[Obsolete(error: true)]` decoy public constructor on every arm to force a compile-time error instead of a silent bind, or a dedicated non-`IntPtr`-convertible handle wrapper type in place of the raw `internal Arm(IntPtr)`. Discovered alongside ADR-134.

**Narrowed by [ADR-148](docs/adr/148-sealed-subclass-constructors.md).** A `CLASS`-kind arm whose public constructor parameters are all bridgeable now exports that constructor. For an arm whose first parameter is `int`-convertible, the exported constructor is an exact match and wins overload resolution over the implicit `int`-to-`nint` conversion into the internal handle constructor, so a positional `new Nap.Deep(12)` now binds to the real constructor instead of crashing. The hazard is unchanged for every `object` arm (no public constructor to export) and for an arm whose constructors are all refused (e.g. an opt-in-marked or nullable-unbridgeable parameter type).
