# Reverse bindings that do not compile on a real package (four ROADMAP items, plus one folded)

- ROADMAP: line text as of 2026-09-21, four items:
  - A (Phase 9): "A bound C# class with an `init`-only property generates a Kotlin setter whose C# thunk does not compile."
  - B (Tooling): "A bound method with an interface-typed parameter and a struct return emits an unresolvable `handleOf(...)`, failing the Kotlin compile."
  - C (Tooling): "The reverse C# shims' `[ModuleInitializer]` sites carry no `CA2255` suppression, so a library consumer with `TreatWarningsAsErrors` fails to compile against a bound package."
  - D (Tooling): "`RirDiagnosticKind.ERROR_KOTLIN_SIGNATURE_COLLISION` exists (`nuget-plugin/.../rir/RirModel.kt:350`) but nothing in the reverse pipeline produces it, so two bound C# members that collapse to one Kotlin signature emit non-compiling Kotlin instead of a diagnosed skip"
  - Folded, E (Phase 9): "A bound class returning an interface declared in a different bound namespace generates non-compiling Kotlin."
- Researched: 2026-09-21, about 25 minutes of source reading and web, then a second pass the same day (about 10 minutes, inside the 25 minute checkpoint) that ran the skipped spikes in the `kn-w3` worktree at `651cb7d0` with .NET SDK 10.0.301. Claims are now **verified by spike**, **verified by reading** or **inferred**; see "Spikes run (2026-09-21)" for seams and observed output.
- Restatement: reverse direction (C# NuGet package declares, Kotlin consumes). A consumer who binds a real package they do not control gets Kotlin stubs and C# shims that compile, or a named diagnostic, never generated source that fails in `compileKotlin` or in the consumer's `dotnet build`.
- Verdict (per sub-item, no ADR drafted for any):
  - A: fix (reader-side, small; plus the ADR-085 bridge `init` accessor if open question 2 is answered (a))
  - B: fix (one emitter file, one live site at `BT:4328`, plus a same-family predicate; the second site is unreachable, spike B4)
  - C: strike (premise is false; the `// <auto-generated>` header already suppresses CA2255, and `GeneratedBindingsCheck` already compiles the reverse shims with warnings as errors)
  - D: fix, and reword the ROADMAP line (premise is half false; the collision IS detected and fatal, it just never goes through `RirDiagnostic`, and its coverage has holes)
  - E: fix, fold with B (the return position is NOT covered by ADR-152's fix; the backlog "Update" is wrong)

Headline: three of the five premises do not survive a read of `main` at `651cb7d0`. C is a phantom, D is already fatal for the common case, and E is a real defect the backlog file believes is closed by construction.

Dated note, 2026-09-21 (spike pass). No verdict was contradicted; all five stand and are now backed by observed output. Four refinements changed the pricing (A, B and E are marked "Spike correction" where they land; D is confirmation):
- A: the recommended detection (string decoder, match `modreq(System.Runtime.CompilerServices.IsExternalInit)`) renders identically for the net8.0 BCL type and a netstandard2.0 in-assembly polyfill, so the ADR-053 style landmine in A4 does not bite that approach. The Kotlin-implementable bridge for an interface `{ get; init; }` is reachable today and fails with CS8854; an `init` accessor on the bridge compiles, so A7 has a cheap fix that belongs in PR 2.
- B: the second site (`buildStructStubMethod`) is unreachable. The reader skips a struct method with an interface-typed parameter (`skipped_unbound_type_reference`), so PR 1 does not thread the flag there.
- E: reachable only when the two C# namespaces map to different Kotlin packages, which by default they do not (every namespace of one package lands in the sanitised `packageId` package). It needs a `namespaceAliases` entry (as `test-library` has) or a second package. Still a fix.
- D: all three gaps the memo listed emit redeclared Kotlin silently (properties, interface methods, `read` beside `ReadAsync`); the class-method collision message is quoted verbatim below.

### A. `init`-only property on a bound class

1. **Verified by reading, and verified by spike.** The class/interface property loop computes `isReadOnly` from the setter's presence and accessibility only: `RD:1816-1819` (`accessors.Setter.IsNil || (setter.Attributes & MemberAccessMask) != Public`). Nothing inspects the setter's signature. The value lands in `RirProperty` at `RD:1853`. Spike: the shipped reader over a net8.0 classlib with `public string Motto { get; init; }` beside `public int Age { get; set; }` reports `"isReadOnly": false` for both, and the strings `modreq` and `IsExternalInit` occur nowhere in the emitted `reverse-ir.json`. Same result for a netstandard2.0 assembly with a polyfilled `IsExternalInit`, and for an interface property `string Label { get; init; }`. The generators then emit, verbatim, Kotlin `var motto: String` with a `set(value)` that invokes `KennelBindings.mottoSetterFn`, and C# `receiver.Motto = Marshal.PtrToStringUTF8(valuePtr)!;` inside `Motto_Set_Thunk` (`KennelRegistration.cs`). Compiling that assignment shape against the probe assembly gives `error CS8852: Init-only property or indexer 'Kennel.Motto' can only be assigned in an object initializer, ...`; the bound-interface thunk `receiver.Label = ...` gives the same CS8852 for `'IBadge.Label'`.
2. **Verified by reading.** The reader cannot see the modreq through its existing decode: it decodes the *property* signature (`TryDecodePropertyType`, called at `RD:1808`), while `modreq(IsExternalInit)` sits on the *setter method's* return type. And the typed decoder throws modifiers away: `SignatureDecoder.GetModifiedType` at `RD:3640-3654` returns `unmodifiedType` for everything except `DynamicAttribute`. Only the string decoder keeps them (`RD:3141-3142`, renders `modreq(<name>)<type>`).
3. **Verified by spike in ADR-058, not re-run here.** `docs/adr/058-csharp-shape-b-structs-in-kotlin.md:119-124` and `:764-765`: an `init` setter's signature blob is `20 01 1F 4D 01 08` against a plain setter's `20 01 01 08`; `0x1F` is `ELEMENT_TYPE_CMOD_REQD` and the coded index resolved to `System.Runtime.CompilerServices.IsExternalInit` (net8.0, SDK 10.0.300). ADR-058 `:172-178` records the class-side CS8852 as verified by a scratch cross-assembly compile.
4. **Verified by spike (the part the fix rests on); handle kinds forced by construction, not printed.** On net8.0 `IsExternalInit` ships in the BCL, so the modifier is a `TypeReferenceHandle` (ADR-058's probe says `TypeRef[19]`). A library that targets netstandard2.0 and polyfills `IsExternalInit` itself declares the type in its own assembly, so the modifier can only be a `TypeDefinitionHandle`. Spike correction: this does NOT bite the recommended detection. A temporary debug print in the reader (reverted) decoded each setter `MethodDefinition` with the existing string decoder `CanonicalSignatureDecoder` (`RD:3084`, parameterless constructor as at `RD:2499`) and printed the return type. Observed, net8.0: `SPIKE setter Motto ret=[modreq(System.Runtime.CompilerServices.IsExternalInit)System.Void]`, `SPIKE setter Age ret=[System.Void]`, `SPIKE setter Label ret=[modreq(System.Runtime.CompilerServices.IsExternalInit)System.Void]`. Observed, netstandard2.0 polyfill: `SPIKE setter Motto ret=[modreq(System.Runtime.CompilerServices.IsExternalInit)System.Void]`, `SPIKE setter Age ret=[System.Void]`. The spelling is identical for both handle kinds, so a `StartsWith("modreq(System.Runtime.CompilerServices.IsExternalInit)")` on that decoder's return type is correct for both. An implementation that instead adds an arm to the typed decoder's `GetModifiedType` (`RD:3640`) must still compare the resolved full name, never the handle kind; that variant was not spiked.
5. **Verified by reading.** Consumers of `isReadOnly` that then do the right thing for free once the reader reports `true`: registrables `BT:935`, `BT:940`, `RB:572`, `RB:790` (getter only, so no setter slot, no setter thunk); Kotlin keyword via `hasSetter` in `buildStubProperty` (`BT:4457`, `val` vs `var` at `BT:4476`); the C# setter thunk body is `"$receiverExpr.${r.property.name} = $callArgs;"` at `ST:1003`, which is the CS8852 line.
6. **Verified by reading.** Shape B structs need no change: `RD:1229-1232` reads `publicSetter` the same way, and ADR-058 Constraint 2 (`:154`, `:492`) verified that object-initializer reconstruction is legal for `init`. Leave `RD:1229` alone.
7. **Verified by reading; consequence verified by spike.** `RB:103` matches a class property against an interface property with `(ip.isReadOnly || !cp.isReadOnly)`. After the fix an `init` property is read-only on both sides, so a class implementing `{ get; init; }` still matches. **Verified by spike (was inferred).** The reader admits an interface declaring `string Label { get; init; }` with no diagnostic, and `IBadgeRegistration.cs` today contains a Kotlin-implementable bridge class whose property is `public string Label { get {...} set {...} }` (ADR-085, `ST:1513` region). Compiling the three candidate shapes against the probe assembly: a `set` accessor gives `error CS8854: 'WithSet' does not implement interface member 'IBadge.Label.init'. 'WithSet.Label.set' cannot implement 'IBadge.Label.init'.`; get-only gives `error CS0535: 'GetOnly' does not implement interface member 'IBadge.Label.init'`; an `init { }` accessor draws no diagnostic (the same compilation reported only the errors quoted here and in A1). So the bridge is broken today (CS8854), would stay broken after a naive reader fix (CS0535), and the working shape is an `init` accessor whose body is unreachable from Kotlin. **Inferred:** emitting that needs the RIR to distinguish "init" from "no setter" (a new `isInitOnly` flag beside `isReadOnly`), since the shim generator cannot otherwise tell them apart. Promoted from Deferred scope to open question 2.
8. **Inferred.** `required` members (C# 11) are orthogonal: `required` is a `RequiredMemberAttribute` on the property plus `SetsRequiredMembers` on constructors, and a `required ... { get; set; }` still has an ordinary setter. The constructor side (a `new T()` thunk without an initializer is CS9035) is a separate, unfiled defect; listed under open questions, not priced here.

### B. Interface-typed parameter plus struct return: `handleOf(...)` with no receiver

1. **Verified by reading.** `wrapInvoke` (`BT:3904-3915`) only opens `nugetTransferScope { ... }` when `hasInterfaceArg` is true. `handleOf`/`handleOfOrNull` are members of the generated `NugetTransferScope` (`BT:5409-5420`) and are what `argConversion` emits for any `RirInterfaceType` argument (`BT:3934-3937`).
2. **Verified by spike (reproduction), site verified by reading.** Reader output for `public Collar Fit(IFeedable guest)` on a bound class, fed to `generateKotlinStubs`, emits verbatim in `Kennel.kt`:
   `fun fit(guest: IFeedable): Collar = memScoped {` ... `nugetCall { err -> fn.invoke(handle.require("Kennel"), handleOf(guest, "Probe.Zoo.IFeedable"), outGirth.ptr, outBells.ptr, err) }` then `Collar(outGirth.value, outBells.value)`.
   There is no `nugetTransferScope { ... }` around the call, while the same file's interface-typed setter has one: `nugetCall { err -> nugetTransferScope { fn.invoke(handle.require("Kennel"), handleOfOrNull(value, "Probe.Zoo.IFeedable"), err) } }`. In the generated `NugetRuntime.kt`, `handleOf` exists only as a member of `internal class NugetTransferScope` (`:441-451`) and `nugetTransferScope` is `internal inline fun <R> nugetTransferScope(block: NugetTransferScope.() -> R): R` (`:462`), so the bare call has no receiver. **Inferred (not compiled):** the failure is an unresolved reference at `compileKotlin`. `buildStubMethod` computes `hasInterfaceParam` at `BT:4160` and threads it to every return branch through `invokeCall` (`BT:4169`), except the `is RirStructType` branch, which builds its own call at `BT:4325-4330` with `hasStringArg = false, hasInterfaceArg = false`. The backlog file's `3821-3843` is this site, drifted. The `hasStringArg = false` there is correct (the whole body is already `= memScoped { ... }`); only `hasInterfaceArg` is wrong.
3. **Verified by reading.** The async and flow arms of that same branch pass `task` / `nugetEnumeration` as the only in-argument (`BT:4311-4317`), so they must keep `false`. The correct expression is `hasInterfaceArg = !isAsync && !isFlow && hasInterfaceParam`. The `Begin`/`Enumerate` halves already thread `hasInterfaceParam` (`BT:4178-4183`, `BT:4415-4416`).
4. **Verified by reading.** Same defect, second site: `buildStructStubMethod`'s struct-return branch at `BT:2462` hard-codes `hasInterfaceArg = false`, and so do its other return branches (`BT:2399`, `2413`, `2433`, `2472`). **Verified by spike (was inferred), Spike correction:** this site is unreachable. For a struct declaring `public int Weigh(IFeedable guest)` and `public Collar Refit(IFeedable guest)`, the reader emits `"kind": "skipped_unbound_type_reference"` for `Weigh(B4.IFeedable)` and for `Refit(B4.IFeedable)`, and the generated `Collar.kt` contains no `weigh`, `refit`, `handleOf` or `nugetTransferScope`. PR 1 does not touch `buildStructStubMethod`; the hard-coded `false` values there are correct by exclusion, and whoever lifts that reader skip inherits the flag.
5. **Verified by reading.** Same family, different predicate: the interface route at `BT:5959` uses `it.type is RirInterfaceType` where the class route uses `isInterfaceLike` (`BT:226-228`, which also covers a collection of interfaces, ADR-155). **Inferred:** unreachable today because `collectionPositionDiagnostics` skips collection positions on bound-interface members (comment at `BT:6660-6663`), so this is a latent trap for whoever lifts that skip, not a live bug.
6. **Verified by reading.** The property setter is already right: `BT:4698` passes `isInterfaceLike(propType)`. The struct-typed setter at `BT:4690` passes `false`, which is correct only while struct components cannot be interface-typed (`docs/backlog/class-typed-handle-components-inside-struct-deferred.md`; **inferred** that interfaces are excluded the same way).
7. **Verified by reading.** (The spiked `Kennel.kt` does carry `import io.github.xxfast.kotlin.native.nuget.internal.nugetTransferScope`, but the probe class also has an interface-typed setter, so the spike does not isolate the method-only case; PR 1's unit test should use a class whose ONLY interface position is the `Fit` parameter.) The import is already there: `BT:3682-3684` adds `import ...nugetTransferScope` whenever any member has an interface parameter, independent of return shape. So the fix is the flag alone.
8. **Verified by reading.** No fixture hits it: `TestDependency/Menagerie.cs` has interface-parameter members returning `string`, `void`, `int`, `string?` (`:177`, `:192`, `:201`, `:224`, `:239`) and none returning a struct.

### C. CA2255 on the reverse shims' `[ModuleInitializer]`

1. **Verified by reading (build artifact in the MAIN checkout, not rebuilt in the spike worktree; re-inspected 2026-09-21: 48 files, 47 with the literal `[ModuleInitializer]` and the `// <auto-generated>` header, and `Interop.cs` the only file without the header and the only one carrying a `CA2255` pragma).** The premise "`GeneratedBindingsCheck` runs only over the forward `Interop.cs`" is false. `PackNugetTask` stages the reverse shims into the same `contentFiles/cs/any/` as `Interop.cs` (`PackNugetTask.kt:50-52`, wired at `NugetPlugin.kt:535-537` and `:573-575`). The packed fixture `test-library/build/nuget/TestLibrary.1.0.0-fixture.*/contentFiles/cs/any/` holds 48 `.cs` files, all 48 contain `ModuleInitializer`, and `GeneratedBindingsCheck/obj/Debug/net8.0/GeneratedBindingsCheck.dll` (built 2026-09-21 07:48, `TreatWarningsAsErrors=true`, `OutputType` library, `GeneratedBindingsCheck.csproj:14`) contains the strings `BoxesRegistration` and `KennelRegistration`. The reverse shims compile under exactly the posture the item says would break them, and `verify.sh:73` and `ci.yml:63` run that build green.
2. **Verified by reading.** The difference between the file that needed the pragma and the 47 that do not is the first line. Every reverse shim starts with `// <auto-generated>` (`ST:1080`, `:1352`, `:1517`, `:2306`, `:2560`, `:3109`); the forward `Interop.cs` starts with `#nullable enable` and has no such header (`test-library/build/generated/ksp/mingwX64/mingwX64Main/resources/Interop.cs:1`; no `auto-generated` string anywhere under `nuget-processor/src/main`).
3. **Verified by spike (was inferred from dotnet/roslyn-analyzers source).** Scratch net8.0 classlib, SDK 10.0.301, `TreatWarningsAsErrors=true`, `EnableNETAnalyzers=true`, `AnalysisLevel=latest-all`, one `internal static` class with a `[ModuleInitializer]` method, compiled one file at a time. With the three-line `// <auto-generated> ... // </auto-generated>` header then `#nullable enable`: `Build succeeded. 0 Warning(s) 0 Error(s)`. Identical file without the header: `Without.cs(6,6): error CA2255: The 'ModuleInitializer' attribute is only intended to be used in application code or advanced source generator scenarios`. With the struct shim's unclosed form (`// <auto-generated>` and no closing tag, `ST:2306`): `Build succeeded.` Without the header and with `AnalysisLevel` left at the SDK default: the same CA2255 error, so the rule is on by default for a net8.0 library and the hazard is real for any un-headered file. Source reading that predicted this: `ModuleInitializerAttributeShouldNotBeUsedInLibraries.cs` calls `context.ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)` and only registers when `OutputKind == DynamicallyLinkedLibrary`. Roslyn treats a file whose leading comment contains `<auto-generated` as generated code, so the rule never analyses the reverse shims. Same project, same analyzers, only the header differs, which is what finding 1 shows empirically.
4. **Verified by reading.** There are five `[ModuleInitializer]` sites today, not the three the backlog lists: static class `ST:1098`, bound class `ST:1368`, bound interface `ST:1533`, struct `ST:2320`, shared runtime `ST:2587`. The forward precedent is `CirRuntimeRenderer.kt:27-35`, pinned by `Tier1RuntimeVersionTest.kt:69-70`.
5. **Inferred.** Other warnings under `TreatWarningsAsErrors`: the `<auto-generated>` header suppresses analyzer (CA/IDE) diagnostics whose analyzers opt out of generated code, which is nearly all of them, but it does NOT suppress compiler warnings (CS). It also turns the nullable context off unless the file says `#nullable enable`, which every shim does, so CS86xx nullable warnings are live in the shims and are exactly what `GeneratedBindingsCheck` polices (see the CS8600 note at `ST:1780`). `unsafe` requires `AllowUnsafeBlocks` in the consumer (an error, not a warning; **inferred** to be set by the package's `build/` props since the check passes). CS1591 is muted in the check (`GeneratedBindingsCheck.csproj`), and the shims are `internal`, so a consumer with `GenerateDocumentationFile` gets no CS1591 from them (**inferred**).
6. **Verified by spike (was inferred).** Adding `.editorconfig` with `[*.cs]` `generated_code = false` beside the headered file turns the clean build into `With.cs(9,6): error CA2255`. The one way a consumer could re-expose CA2255 is an `.editorconfig` with `generated_code = false` matching the contentFiles path in the NuGet cache. That is a consumer deliberately overriding the generated-code convention on someone else's files; not a supported posture.

### D. `ERROR_KOTLIN_SIGNATURE_COLLISION` is never produced

1. **Verified by reading.** The enum constant is at `RM:388-389` (the ROADMAP's `:350` drifted). No producer exists: not in `RD` (no `signature_collision` string in `Program.cs`), not in `RB`, not in `BT`. The only appearance in a test is injected JSON (`OverloadGenerationTest.kt:462-476`) proving the *consumer* `validateDiagnostics` (`BT:6700-6712`) throws on any `ERROR*` kind (`OverloadGenerationTest.kt:228-238`).
2. **Verified by reading and by spike. This overturns the item's second half.** Spike: reader output for `public sealed class Meths { public int Read() => 1; public int read() => 2; }` fed to `generateKotlinStubs` throws `java.lang.IllegalArgumentException` with the full message ``[nuget] Kotlin signature collision: `method|instance|DMeths.Meths|Read|()|System.Int32` and `method|instance|DMeths.Meths|read|()|System.Int32` both map to `fun read()`. Expose a differently named C# adapter.`` No Kotlin file is returned. The message has no `[nuget:<packageId>]` prefix and no diagnostic kind string. Note `generateCSharpShims` has no such check and returned `MethsRegistration.cs` normally; harmless in the task graph only if the Kotlin task fails first (**inferred**, task ordering not traced). Collisions ARE detected and ARE fatal before any file is written: `validateKotlinSignatures` (`BT:6714-6763`), called from `generateKotlinStubs` at `BT:375`. It groups every bridgeable method of every non-generic `RirClass` by `scope:camelCaseName(kotlinCollisionType,...)` and every constructor by its parameter key, and `require(false)`s with "[nuget] Kotlin signature collision: `A` and `B` both map to `fun x(...)`. Expose a differently named C# adapter." It is a bare `IllegalArgumentException`, never a `RirDiagnostic`, so it bypasses `formatDiagnostic` (`BT:6790-6800`), carries no package id, and reports only the first colliding group.
3. **Verified by reading.** Async members are inside that check: an async method is a `RirRegistrable.Method` on the class route (`RB:1235`; the `asyncKind` filters at `RB:305`, `:315`, `:560` are the struct/interface/generic routes). So without ADR-153's reader-side fold (`RD:1700`, `FoldCancellationOverloads` at `RD:2523`), `FooAsync()` beside `FooAsync(CancellationToken)` would be a fatal generation error, not non-compiling Kotlin. The fold is still needed (it turns a fatal into a binding), but the ROADMAP sentence "load-bearing only because this gap exists" is wrong, and ADR-153 `:129-130` ("Without this the consumer's Kotlin does not compile") is imprecise for classes.
4. **Verified by reading.** ADR-155's `skipped_overload_set` is a deliberate, narrower policy on top, not a workaround for a missing check: `collapsedOverloadSets` (`RB:1000-1018`) skips the whole set only when a collection parameter is what collapsed it, and its own comment (`RB:994-996`) says every other collision shape keeps the hard failure. `collapsedOverloadDiagnostics` is at `BT:6673-6697`.
5. **Verified by reading. The real holes in `validateKotlinSignatures`:**
   - It skips generic class definitions entirely (`BT:6725`, `filterNot { it.typeParameters.isNotEmpty() }`).
   - It never looks at `RirInterface` or `RirStruct` members (`filterIsInstance<RirClass>()`). **Verified by spike:** `public interface IMeths { int Read(); int read(); }` generates with no error and no diagnostic, and `IMeths.kt` contains `fun read(): Int` twice (lines 12 and 13); `IMethsHandle.kt` implements both. The struct half was not spiked.
   - It never looks at properties. Two C# properties `Name` and `name` (legal, case-sensitive) both render `name`; a redeclaration error in Kotlin. **Verified by spike:** `Props { string Name; string name; }` generates with no error and no diagnostic, and `Props.kt` contains `var name: String` twice (lines 41 and 59).
   - It keys on `method.name.toMethodCamelCase()` (`BT:6737`), while the emitted name is `kotlinMemberName(cls, method)` (`BT:4079-4085`), which strips `Async`. **Inferred:** the keep rule (`cls.methods.any { it.name == stripped }`) closes the obvious `Read`/`ReadAsync` case, but it compares the C# name exactly, so `read` beside `ReadAsync` slips through to a Kotlin redeclaration. Rare. **Verified by spike (was inferred):** `class A { int read(); Task<int> ReadAsync(); }` generates with no error, and `A.kt` contains `suspend fun read(): Int` (line 35) and `fun read(): Int` (line 49). That `suspend` does not disambiguate is the D6 rule, still inferred (not compiled).
6. **The collision rule (inferred from the Kotlin spec, consistent with the code).** Kotlin/Native has no JVM erasure rule; two functions conflict when they are declared in the same scope with the same name and the same value-parameter types after mapping. Return type, `suspend`, parameter names and default values do not disambiguate; nullability does (`String` vs `String?` are distinct overloads), which `kotlinCollisionType` (`BT:6765-6787`) already models by appending `?`. A property and a function may share a name. Static and instance members land in different scopes (companion vs class), which the `scope:` prefix models.
7. **Verified by reading.** Many-to-one type mapping is what makes a collision reachable from ordinary C#. Today `kotlinType` (`BT:2759-2787`) is one-to-one for primitives (`bool`, `byte`, `short`, `int`, `long`, `float`, `double`, `char`); the only many-to-one mapping is collections (ADR-155), which has its own skip. So beyond collections the reachable triggers are case-folded names only. ADR-057 `:358-364` says the same: the collision test is synthetic by design.
8. **Verified by reading.** ADR-057 `:245-256` already decided the policy: fatal, name both managed signatures, and "Add a structured `error_kotlin_signature_collision` diagnostic ... and make the centralized diagnostic reporter throw on `error_*` entries". The reporter half shipped; the structured producer did not. D is finishing ADR-057, not a new decision.

### E. Cross-namespace interface in the return position

1. **Verified by reading.** An interface-typed return lowers through an unqualified call to `nuget${Name}Value(...)`: class method `BT:4273`, `BT:4279`; class property `BT:4573`, `BT:4581`; static route `BT:1282`; collection element read `BT:2663`, `BT:2672`; interface route `BT:6095`, `BT:6103`; callback argument `BT:6571-6572`.
2. **Verified by reading.** That function is `internal fun nuget${iface.name}Value(...)`, emitted into the interface's own file and therefore its own Kotlin package (`BT:6378-6387`, called at `BT:6337`).
3. **Verified by reading.** The class-file import collector `interfaceImports` (`BT:1791-1801`) emits only `import $pkg.${type.name}`. The one place that imports the resolver too is the bridge-slot collector `slotHandleImports` at `BT:1716` (`"import $pkg.$name", "import $pkg.nuget${name}Value"`). A grep for `import.*nuget.*Value` in `BT` finds that line and nothing else.
4. **Verified by spike (reproduction).** With namespaces `Probe.Kennel` and `Probe.Zoo` aliased to Kotlin packages `probe.kennel` and `probe.zoo`, the generated `probe/kennel/Kennel.kt` has the import block ending `import probe.shapes.Collar` and `import probe.zoo.IFeedable` and nothing else from `probe.zoo`, yet its body contains `return nugetIFeedableValue(requireNotNull(ptr) {` (method `resident()`) and `return ptr?.let { nugetIFeedableValue(it) }` (property `favourite` getter). ## Open what-questions

1. A: should an `init`-only property surface as a plain `val`, with or without an `info_*` diagnostic? Recommendation: plain `val`, no diagnostic. Kotlin consuming a Java final field or getter-only bean does the same, and nothing is lost that Kotlin could express post-construction. Human decision: pending.
2. A: an interface `{ get; init; }` is reachable (spiked: reader admits it, bridge emits `set`, CS8854). Should PR 2 (a) emit an `init` accessor on the ADR-085 bridge, carried by a new `isInitOnly` RIR flag, so Kotlin can still implement the interface with a `val`, or (b) skip that interface's Kotlin-implementable bridge with a diagnostic? Recommendation: (a), folded into PR 2 per the "do not grow the phase with deferrals" feedback; the spike shows `init { }` on the implementer compiles and the handle-backed direction only needs the setter slot dropped. Human decision: pending.
3. D: keep collisions fatal (ADR-057) or change to "skip the whole set with a diagnostic" as the ROADMAP line's wording implies and ADR-155 Q8 does for collections? Recommendation: keep fatal for now; the only non-collection trigger is case-folded names, which is too rare to justify reopening ADR-057, and `admit(...)`/exclusion (ADR-154) gives a user an escape hatch for a package they do not control (**inferred**, not checked that exclusion works per member). If the human prefers skip, that needs an ADR superseding the relevant paragraph of ADR-057.
4. C: strike outright, or strike and add the five pragma pairs for symmetry with `CirRuntimeRenderer.kt:33-35`? Recommendation: strike, add only the header-pin test. The inverse consistency fix (give forward `Interop.cs` the `// <auto-generated>` header and drop its pragma) changes nullable-context and analyzer behaviour for the whole forward file and is NOT recommended here.
5. E + B: one PR or two? Recommendation: one; same file, same fixture class, same failure mode.
6. Should the ROADMAP/backlog text for C, D and E be corrected immediately (before any code), since three agents could otherwise pick them up on false premises? Recommendation: yes, a docs-only commit by the documenter.
