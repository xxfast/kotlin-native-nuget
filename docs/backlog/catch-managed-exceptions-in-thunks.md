# Catch managed exceptions in registration thunks and propagate across the ABI as Kotlin exceptions

> Extracted verbatim from `ROADMAP.md` (Phase 11: Reverse exception handling) in the 2026-08-31 roadmap slim-down.

**Catch managed exceptions in registration thunks and propagate across the ABI as Kotlin exceptions** (mirror of ADR-023/024). Confirmed live, not just theoretical, by [ADR-087](docs/adr/087-kotlin-slot-exceptions.md) stage 2 (Phase 13 Wave 2): a Kotlin-implemented C# interface member can now throw a catchable exception when C# calls its bridge member directly, but the identical throw still terminates the host the moment the call *originates in Kotlin* and reaches that member indirectly through an ordinary reverse-bound method (`Sanctuary.Introduce` calling `IFeedable.Describe()` internally): every `[UnmanagedCallersOnly]` reverse thunk today has no error out-parameter and no catch, so any managed exception thrown anywhere underneath one is fatal regardless of cause, ADR-087's own envelope included. This item is that fix, generalized to every reverse thunk rather than one interface-slot special case: an error out-parameter on every thunk, a check at every generated Kotlin stub call site, and a registration contract-hash bump (mirroring the `kotlin_bridge_v2` bump ADR-087 already did for interface slots), needing its own ADR. `IntegrationTests/MenagerieRoundTripTests.cs`'s `KotlinNoVacancy_DescribeThrows_MapsToKotlinInvalidOperationException` is `[Fact(Skip = ...)]` waiting on exactly this.
