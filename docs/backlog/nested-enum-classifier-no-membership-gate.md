# A nested enum has no exported-handle gate in the classifier's enum branch

**A `enum class` declared nested inside another exported class is bound and referenced at a member position (now correctly spelled `global::Namespace.Outer.Mode` by `nestedCsName()`), but it is never actually declared**, since `NugetProcessor.kt`'s `rootEnums` collection excludes a nested enum from the root buckets it declares from. The generated reference therefore names a type that does not exist, `CS0246`, inferred from reading, not reproduced by a fixture. `ForwardBridgeTypeClassifier.kt`'s enum branch classifies any `ClassKind.ENUM_CLASS` declaration as an `ObjectHandle` with no check against `context.exportedObjectHandles` or an equivalent membership set, unlike the sealed-class branch's `qualifiedName in context.exportedObjectHandles` gate (see the [ADR-105 post-implementation note](https://github.com/xxfast/kotlin-native-nuget/blob/main/docs/adr/105-sealed-property-position.md#post-implementation-note-the-classifier-mint-is-gated-and-two-inferred-claims-are-now-verified)). The same missing gate lets an out-of-scope *dependency* enum (one never admitted into the export set at all) get spelled instead of skipped named, the same class of hole a membership gate would also close. It went unnoticed because every enum fixture in the tree so far is top-level; nothing exercises a nested one. The fix is a membership gate on the enum branch (mirroring the sealed-class one), not a spelling change: `nestedCsName()` itself is correct. Discovered alongside the nested sealed-subclass member-position fix ([ADR-009](https://github.com/xxfast/kotlin-native-nuget/blob/main/docs/adr/009-sealed-class-mapping.md)).
