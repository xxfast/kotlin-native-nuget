# No way to observe live `StableRef` count, so every handle leak so far was found by reading source

> Added 2026-09-09 as the first item of the Performance & Resource Hygiene section.

**Every bridged object, collection, callback and interface bridge crosses as a `StableRef`, and nothing counts them.** Three handle leaks have been found to date (the collection-parameter handle on a throwing callee, closed by [ADR-073](../adr/073-map-and-set-parameters.md); the per-element `Wrap<T>` box, closed by [ADR-099](../adr/099-nested-collection-components.md); the outer returned-collection handle, still open in Phase 4) and all three were found by an agent noticing a `Dispose` sitting after a `throw` with no `finally`, then confirmed with coverage data showing the `Dispose` line at zero hits. None were found by measurement, because the bridge exposes no measurement: ~150 `StableRef.create`/`asStableRef`/`.dispose()` sites across `exports/` and `forward/` in `nuget-processor` mint and free handles with no shared counter.

The two seams a harness needs already exist. [ADR-054](../adr/054-reverse-bridge-registration-observability.md)'s `NUGET_INTEROP_TRACE=1` already logs every registration and crossing. `IntegrationTests/BidirectionalTests.cs` and `MenagerieRoundTripTests.cs` already drive `GC.Collect()` plus `WeakReference` to prove the .NET side releases; what is missing is the Kotlin side of the same assertion.

Proposed shape, in order:
1. A single Kotlin-side `nugetLiveHandles(): Long` counter incremented in one shared `nugetRetain`/`nugetRelease` pair that every generated `StableRef.create`/`dispose` routes through, exported as one interface-agnostic runtime slot beside ADR-089's `WeakenGcHandle`/`ResolveGcHandle` (which moves `NUGET_RUNTIME_CONTRACT_HASH`, so it is an ADR). Compiled in always, not debug-only: an atomic increment per crossing is cheaper than the P/Invoke it sits next to, and a counter you cannot read in production is one you will not trust.
2. A `[Collection]`-scoped xunit fixture that snapshots the count, runs N iterations of a crossing, disposes, `GC.Collect()` + `WaitForPendingFinalizers()`, and asserts the count is back to baseline. One theory per crossing family: primitive call, `string`, each collection kind as parameter and return, callback subscribe/unsubscribe, interface bridge in both directions, `Flow` enumerate-to-completion and enumerate-then-abandon, suspend cancel.
3. Re-run with the still-open Phase 4 returned-collection leak deliberately triggered, to prove the harness is red where source reading says it should be, before trusting it green anywhere else.

Out of scope: the separate "does Kotlin's GC actually free the object once its last `StableRef` is disposed" question, which needs a Kotlin-side weak reference and a forced GC and is its own roadmap line.
