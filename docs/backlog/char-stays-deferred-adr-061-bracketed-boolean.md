# `Char?` stays deferred, and ADR-061 bracketed it with `Boolean?` incorrectly.

> Extracted verbatim from `ROADMAP.md` (Phase 4: Rich type support) in the 2026-08-31 roadmap slim-down.

**`Char?` stays deferred, and ADR-061 bracketed it with `Boolean?` incorrectly.** It is not the same problem as the nullable-Boolean width fix ADR-069 just closed: Kotlin `Char` is 2-byte UTF-16 against C#'s default 1-byte ANSI `char` marshalling. Same-shaped follow-up (a width mismatch at a nullable-primitive seam), different fix, deliberately out of scope for [ADR-069](docs/adr/069-nullable-boolean-marshalling.md), which the human approved deferring separately. **Corrected by [ADR-098](docs/adr/098-narrow-primitive-and-char-collection-components.md):** this item's own proposed fix, "needs a `UShortVar` + `ushort` narrowing on the wire, not a `MarshalAs` attribute", was wrong on both halves. Kotlin already emits `KChar` as `unsigned short`, no Kotlin-side change was needed, and `[MarshalAs(UnmanagedType.U2)]` was the chosen and verified-correct fix, on ADR-069's exact precedent. ADR-098 ships that attribute at every ordinary `Char` position and at `Char` collection components; what remains open here, narrowly, is only the has-value fan-out for a bare `Char?` (`hasValueFanOutInner()` has no `Char` case), tracked below.
