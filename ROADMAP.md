- [x] **There is no export set: the processor bridges every public declaration it can see.** `NugetProcessor.process()` takes `resolver.getAllFiles()` with no filter, which is the line above meant literally — *all* public declarations. The `rootPackage` in `nuget { publish { } }` looks like the scoping knob and is not one: it only ever feeds `mapPackageToNamespace` (Phase 3), so it renames the C# namespace while the declaration set stays global, and that function even has an explicit branch that maps a package *outside* `rootPackage` anyway. Applying the plugin to a module that also holds unrelated public API therefore tries to bridge that API too, and any construct the forward direction cannot express there becomes a build break in generated code the user never wrote. This is MF-001 (declaration-level export scoping): an include/exclude mechanism, an annotation, or an effective package filter. First consumer to hit it was NYTimes-KMP (its BUG-003), which pays for it with a dedicated `:app:windows` export module whose `build.gradle.kts` carries a `TODO` explaining why the module exists at all. Verified directly: `getAllFiles()` and every `rootPackage` use site were read in source. Prior art for the decision is Swift Export and ObjC Export, which both had to answer "which declarations leave the module". **Done:** [ADR-063](docs/adr/063-forward-declaration-level-export-scoping.md) adds `publish { include(...); exclude(...) }`, mirroring `bind { include/exclude }` verb-for-verb (exclude wins, prefix match); an empty `include` defaults to `rootPackage` when set, so `rootPackage` now scopes as well as renames (a deliberate, documented behaviour change). A reverse-bound package (from `dependencies { dependency(...) { bind { } } }`) is always exported regardless of `include`/`exclude`, since `test-library`'s own forward/reverse round trip broke on the first cut of this feature when a bound package was dropped from scope.

## Phase 8: Ecosystem — consuming NuGet packages from Kotlin

- [x] Map C# structs (value types): **not** blittable pass-by-value vs boxed handle, the framing this line originally used. Both were dead ends: pass-by-value is not expressible in this project's architecture (a hand-written `CStructVar` cannot be used in a Kotlin/Native `CFunction`, only a cinterop-generated one, which would need a per-target build stage this project deliberately doesn't have), and a boxed `GCHandle` destroys value semantics (`close()`, `Cleaner`, reference equality on what should be a value type). The actual answer is a third option neither name named: **component decomposition**, no struct ever crosses the wire. A struct parameter expands to one ABI argument per component; a struct return expands to `void` + one out-pointer per component. C# reconstruction is recursive: the outer struct's shape decides how a component is *placed*, the inner struct's shape decides how it is *built*, so all four Shape A/B nesting combinations (A-in-A, B-in-A, A-in-B, B-in-B) work with no rules of their own, at any depth and across a Kotlin package boundary. ## Tooling & Test Integrity

Fallout from [ADR-053](docs/adr/053-nullable-reference-types-in-kotlin.md) (reverse nullability), the first fixture to exercise the reverse bridge realistically. It flushed out four latent defects, **two of which were phantoms of stale build state**, and the debugging cost was dominated by having no way to observe the bridge and no way to trust the build. These items exist so the next feature does not pay that cost again.

**Rejected: a `scripts/verify.sh --fast` mode.** It was proposed on the theory that agents hand-patch generated output and the NuGet cache because the sanctioned path is too slow. Measurement kills that theory: verify is 38s clean-room after a source change, 18s warm. Nobody cheats to save 14 seconds. Agents did it because they were being sloppy, which is a discipline problem, and the `PreToolUse` guardrail now makes it impossible. Worse, the only real saving came from skipping `:test-library:clean`, which is precisely what produces a truncated `Interop.cs` (see the KSP bug below), so a fast mode would have handed agents a *sanctioned* way to manufacture the phantom bugs this whole section exists to prevent. Do not re-add it.

- [x] **Reverse-bridge registration observability: always-on self-check first, trace second.** The [ADR-041](docs/adr/041-kotlin-to-csharp-call-mechanism.md) function-pointer table was unobservable: nothing could report which `nuget_{ns}_{type}_register` exports actually fired, so "did registration work?" was only answerable by bisecting. The research found that an opt-in trace, the original framing of this item, is the weaker half of the fix: nobody enables a trace for a bug they don't already suspect, and in the ADR-053 hunt nobody suspected registration. ## Future Improvements

- Support flat/unnested sealed class hierarchies (subclasses as top-level in same namespace)
- KSP incremental processing if build times become a concern on large libraries. Has a prerequisite now: the forward processor's two generated outputs declare `Dependencies.ALL_FILES` (see the completed item above, `NugetProcessor.kt`), which deliberately opts the processor out of incrementality to close a dropped-suspend-functions bug permanently. Any future incrementality work must first restore a correct, complete per-file dependency set instead of a hand-maintained bucket list, the exact mistake that caused the bug
- Map data classes to C# `record class` if a safe `with`-expression pattern can be found (see [ADR-008](docs/adr/008-data-class-mapping.md))
- Verify Kotlin GC actually frees objects after all StableRefs are disposed (requires Kotlin-side weak references + GC trigger — not feasible in standard unit tests)
- Memory leak detection tooling for bridged objects in CI
- Object identity preservation (caching wrappers) if profiling shows allocation overhead is significant
- Custom type mappers for arbitrary third-party dependency types the plugin will never hardcode (escape hatch). Known stdlib types such as `kotlin.time.Instant` are Phase 4 first-class mappings instead, not this item
- Pure-JVM ECMA-335 metadata reader + NuGet v3 client, dropping the .NET SDK prerequisite from the Kotlin-side build (synthesis D1) — no plugin in this space runs prerequisite-free; a genuine ergonomic edge
- Hand-written C# shim escape hatch for API members outside the auto-bridgeable subset (spm4Kmp's bridge-folder model, synthesis D2)
- Local-feed dev loop: let a C# consumer iterate against a locally built `.nupkg` (local NuGet feed / `ProjectReference`) before publishing (KMMBridge-style local-vs-published dual flow, synthesis D6). The basic point-at-a-folder consumption flow is already documented in [getting-started](docs/topics/getting-started.md); what's open is the dev-loop story around it: cache-safe re-publishes of a changed `.nupkg` (the same-version-changed-contents hazard CLAUDE.md documents; the per-build immutable fixture versioning solves it only for this repo's own fixtures)
- First-class Gradle publishing workflow for generated NuGet packages: add a `publishNuget` task and DSL that mirror Gradle's Maven publishing APIs, depend on `packNuget`, and publish the resulting `.nupkg` to NuGet.org or a private feed. Supply feed URLs and credentials through Gradle providers or environment variables rather than checking them into the build. The goal is a Kotlin-native workflow that does not require library authors to invoke `dotnet nuget push` themselves
- Publish to GitHub Packages as a secondary registry, mirroring KStore. Mechanically straightforward: a Gradle plugin is just the plugin jar plus its marker, and `maven-publish` targets `maven.pkg.github.com` like any other Maven repo. The catch is that [GitHub Packages requires an access token even to read public packages](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-apache-maven-registry), and plugin resolution happens in `pluginManagement` before anything else. So a consumer would need credentials in `settings.gradle.kts` just to see the plugin, which is precisely the friction the Plugin Portal exists to remove. Worth it only as a mirror alongside the primary registries, never as the sole channel

- Swap the forward *reader* from KSP to a K2/IR compiler plugin, **if and when the compiler plugin API stabilizes**. Deliberately scoped to the reader only: the Gradle plugin's orchestration (linking, packaging, the whole reverse `nuget*` task chain around `dotnet`/`NugetMetadataReader`) is build-system work and stays in Gradle regardless. What the drop buys: expression-level information KSP structurally cannot see (default parameter value expressions, inline bodies, compile-time constants, the compiler-synthesized data-class members the CIR currently re-materializes by hand); injecting the `CNameExports.kt` side directly as IR instead of KotlinPoet-generated source, removing the second compilation round and the "generated Kotlin must itself compile" bug class; and sidestepping KSP-specific crash surface (the ADR-074 duplicate-plan family). What it costs today, and why this waits on stability: the plugin API breaks per Kotlin version while KSP is the supported facade, `Interop.cs` is a foreign-language output that fits Gradle's task graph (up-to-date checks, caching) better than a compiler extension, generated-source-on-disk is the inspectable evidence the project's whole stale-state debugging discipline leans on, and IDE resolution of injected declarations needs K2 IDE plugin support. Trigger to revisit early: a feature that needs expression-level info (default *values* baked into C#, beyond ADR-091's omitting-overload approach) or a blocking KSP defect
